# คู่มือผู้ดูแลระบบ: การจัดการและนำเข้าข้อมูล (ค้นหาสิทธิ / NHRC RAG)

คู่มือนี้ครอบคลุมเฉพาะ pipeline ข้อมูลที่ระบบ "ค้นหาสิทธิ" ใช้งานจริงในปัจจุบัน
(Obsidian vault → ทำดัชนี → เว็บแอป) — คนละระบบกับ `docs/IMPORTING.md` ซึ่งอธิบาย
เส้นทางนำเข้าเอกสารแบบ Supabase-only ของ `ChatWorkspace`/`/admin/import` ที่ยังไม่ได้ใช้งานจริง

## 1. ภาพรวมของ pipeline

```
Obsidian vault (.md files)
        │  python setup_obsidian_index.py
        ▼
data/nhrc_index.json      ← metadata ของทุกเอกสาร (ใช้ทำตัวกรอง/browse)
data/nhrc_content/*.txt   ← เนื้อหาเต็มของแต่ละเอกสาร (ใช้แสดงผล + ป้อนให้ AI)
data/nhrc_graph.json      ← กราฟความสัมพันธ์ประเด็นสิทธิ (หน้า /knowledge/graph)
data/nhrc_documents/*.pdf ← ไฟล์ต้นฉบับที่คัดลอกมา (ถ้าเจอคู่กับโน้ต)
        │  node web/scripts/embed-nhrc-documents.mjs
        ▼
Supabase (nhrc_embeddings, halfvec) ← เปิดใช้ semantic search ใน Ask NHRC
```

Vault ต้นทางอยู่ที่ `D:\back up\รายงานและข้อเสนอแนะ กสม` (พาธถูกกำหนดใน
`setup_obsidian_index.py`'s `vault_path` — เปลี่ยนได้ถ้าย้ายเครื่อง)

## 2. โครงสร้างโฟลเดอร์ในวอลต์และการเพิ่มเอกสารใหม่

แต่ละหมวดหมู่เอกสาร (`DOCUMENT_CATEGORIES` ใน `web/src/lib/nhrc/types.ts`) ผูกกับ
โฟลเดอร์ที่มีตัวเลขนำหน้าคนละโฟลเดอร์ในวอลต์ (`01 ...` ถึง `10 ...`) มีเทมเพลตพร้อมใช้
สำหรับหมวดที่ยังว่าง/เพิ่งเปิดอยู่ที่ `docs/vault-templates/*.md` — เปิดไฟล์เทมเพลตของ
หมวดที่ต้องการ คัดลอกโครงสร้าง (frontmatter, หัวข้อ `##` ที่กำหนด) แล้วเขียนเนื้อหาจริงทับ

ข้อควรระวังเวลาเขียนโน้ตใหม่:

- **ชื่อไฟล์** กลายเป็นส่วนหนึ่งของ `document_id` โดยตรง — หลีกเลี่ยงอักขระที่ Windows
  ห้ามใช้ (`: / \ * ? " < > |`) และไฟล์เนมที่ยาวเกินไป (ดู commit "Fix filename length
  issues for cross-platform compatibility" ถ้าเจอปัญหา path ยาวเกิน)
- **Frontmatter `tags`** ควรใส่แท็กที่มีความหมายจริง (ไม่ใช่แค่ `["ประเด็นสิทธิ"]` ที่เป็น
  ป้ายหมวดหมู่กว้าง ๆ) เพราะกลายเป็นคำสำคัญ (keywords) ที่ใช้ค้นหา
- เอกสารประเภท "งานวิจัย"/"กฎหมาย"/"ตราสาร" ควรมีหัวข้อ `## สาระสำคัญ` เพราะระบบใช้ส่วนนี้
  เป็นบทสรุปที่ป้อนให้ AI แทนการตัดสุ่มจากตัวเอกสาร (ดู `src/obsidian_parser.py`)
- เนื้อหาที่เขียน/สรุปด้วย AI ต้องมีบรรทัดกำกับความไม่แน่นอนและลิงก์แหล่งทางการเสมอ
  (ดู memory "Legal content accuracy convention" — เช่นบรรทัด "ควรตรวจสอบวันที่/มาตราละเอียด
  กับต้นฉบับทางการก่อนอ้างอิงจริง")

## 3. อัปเดตข้อมูล (รันทุกครั้งหลังแก้/เพิ่มไฟล์ในวอลต์)

**วิธีที่แนะนำ:** ดับเบิลคลิก **`sync-content.bat`** ที่โฟลเดอร์หลักของโปรเจกต์
(`D:\human-rights-rag\sync-content.bat`) รันทีเดียวจบทั้ง 2 ขั้นตอนด้านล่าง
(รีเซ็ตดัชนี + อัปเดต embeddings) ไม่ต้องเปิด terminal เอง

เพิ่มเนื้อหาใน Obsidian แล้ว**ไม่ขึ้นเว็บอัตโนมัติ** ต้องรันไฟล์นี้ (หรือ 2 ขั้นตอนย่อยด้านล่าง)
ก่อนเสมอ — ยังไม่มีระบบ auto-sync แบบเรียลไทม์

รันเสร็จแล้วต้อง restart dev server ในเครื่อง (หรือรอ deploy รอบถัดไปสำหรับเว็บจริง)
ถึงจะเห็นการเปลี่ยนแปลง

### สิ่งที่ `sync-content.bat` ทำภายใน (แยกรันเองได้เหมือนกันถ้าต้องการ)

**ขั้นที่ 1 — รีเซ็ตดัชนี:**

```bash
python setup_obsidian_index.py
```

สคริปต์นี้จะ: parse วอลต์ทั้งหมดใหม่ → เขียน `data/nhrc_index.json`,
`data/nhrc_content/`, `data/nhrc_graph.json` → คัดลอก PDF ต้นฉบับที่หาเจอไปไว้
`data/nhrc_documents/` → รันชุดทดสอบค้นหาแบบง่ายให้ดูท้ายสุด

**บน Windows** ถ้าเจอ `UnicodeEncodeError` ตอน print (เพราะ terminal เป็น cp1252)
ให้สั่งรันด้วย (`sync-content.bat` ตั้งค่านี้ให้แล้วอัตโนมัติ):

```bash
PYTHONIOENCODING=utf-8 python setup_obsidian_index.py
```

ขั้นตอนนี้ไม่แตะ Supabase/embeddings เลย — เป็นการรีเซ็ตเฉพาะไฟล์ JSON ในเครื่อง/repo
เท่านั้น ปลอดภัยที่จะรันบ่อย ๆ

**ขั้นที่ 2 — อัปเดต embeddings สำหรับ semantic search (Ask NHRC):**

Ask NHRC ต้องการ Gemini embeddings ที่เก็บใน Supabase (`public.nhrc_embeddings`)
เพื่อค้นแบบเข้าใจความหมาย (ไม่ใช่แค่จับคำตรงตัว) หลังเพิ่มเอกสารใหม่/แก้ไขเนื้อหาแล้ว
รีเซ็ตดัชนีตามขั้นที่ 1 ต้องรันคำสั่งนี้ต่อเพื่อ backfill embedding ของเอกสารใหม่:

```bash
cd web
node scripts/embed-nhrc-documents.mjs
```

ต้องมี `GEMINI_API_KEY` และค่า Supabase (`NEXT_PUBLIC_SUPABASE_URL`,
`SUPABASE_SECRET_KEY`) ตั้งไว้ใน `web/.env.local` ก่อน สคริปต์นี้จะข้ามเอกสารที่มี
embedding อยู่แล้ว (เขียนซ้ำเฉพาะที่จำเป็น) เพราะฉะนั้นรันซ้ำได้อย่างปลอดภัย

**ถ้าลืมรันขั้นตอนนี้** ระบบไม่ error แต่ Ask NHRC จะเงียบ ๆ fallback ไปใช้การค้นหาแบบ
จับคำตรงตัวแบบเดิม (`repository.ts`'s `findRelevantCases`) ซึ่งด้อยกว่ามาก
เอกสารใหม่จะแทบไม่ถูกดึงมาตอบเลยถ้าคำถามไม่ได้ใช้คำเดียวกับในเอกสารเป๊ะ ๆ —
เป็นสาเหตุของบั๊ก "AI มีความรู้จำกัด" ที่เคยเจอมาแล้วครั้งหนึ่ง

## 4. เอกสารต้นฉบับ (PDF) ผิด หรือหาไม่เจอ

ปุ่ม "เปิดเอกสารต้นฉบับ" ในหน้ากรณีมาจากไฟล์ที่จับคู่ตาม**ชื่อไฟล์ตรงตัวเป๊ะ**
ไม่ใช่การตรวจเนื้อหา — `_find_case_pdf` ใน `src/obsidian_parser.py` มองหาไฟล์
`ปี <พ.ศ.>/<ชื่อไฟล์บันทึกไม่รวม " - บันทึก">.pdf` ในวอลต์ ถ้าชื่อไม่ตรงเป๊ะแม้แต่
เว้นวรรค/เครื่องหมายเดียวจะไม่เจอ

**กรณีไม่มีไฟล์ต้นฉบับเลย (ขึ้น "ยังไม่มีไฟล์ต้นฉบับ"):**
1. ตรวจว่ามีไฟล์ PDF ของกรณีนั้นอยู่ในโฟลเดอร์ `ปี <พ.ศ.>` ของวอลต์จริงหรือไม่
2. ถ้ามีแต่ชื่อไม่ตรง ให้เปลี่ยนชื่อไฟล์ PDF ให้ตรงกับชื่อไฟล์บันทึก `.md` เป๊ะ ๆ
   (ตัด " - บันทึก" ออก)
3. รัน `python setup_obsidian_index.py` ใหม่เพื่อคัดลอกเข้า `data/nhrc_documents/`

**กรณีไฟล์ที่แนบมาผิด (เป็นของกรณีอื่น):** มักเกิดจากไฟล์ PDF ต้นทางถูกตั้งชื่อผิด/
ซ้ำกับอีกกรณีหนึ่งตั้งแต่ต้น (ระบบไม่ได้ตรวจเนื้อหาไฟล์ มีแค่จับคู่ชื่อ) — ตรวจสอบชื่อไฟล์
PDF จริงในโฟลเดอร์ `ปี <พ.ศ.>` แก้ให้ตรงกับกรณีที่ถูกต้อง แล้วรีเซ็ตดัชนีใหม่เช่นกัน

**สำหรับเอกสารประเภท "general"** (งานวิจัย/กฎหมาย/ตราสาร) ไม่มี PDF สแกน —
"แหล่งที่มา" คือ URL ที่เขียนไว้ในหัวข้อ `## ลิงก์...` ของโน้ตเอง แก้ลิงก์ผิดได้โดยแก้
ข้อความในโน้ตนั้นตรง ๆ แล้วรีเซ็ตดัชนี ไม่ต้องยุ่งกับไฟล์ PDF

**บนโปรดักชัน (Vercel) มีอีกชั้นหนึ่ง:** `data/nhrc_documents/` ไม่ได้ขึ้นไปกับ deploy
(ไฟล์ใหญ่/gitignored) เว็บจริงจึงเสิร์ฟ PDF ผ่าน Google Drive แทน โดยอ่าน mapping จาก
`data/nhrc_pdf_drive_map.json` (document_id → Drive file ID) ถ้าแก้ไฟล์ PDF ในเครื่องแล้ว
แต่เว็บจริงยังโชว์ไฟล์เก่า/ผิดอยู่ ต้องอัปโหลดใหม่ด้วย:

```bash
python scripts/upload_pdfs_to_drive.py
```

สคริปต์นี้**ข้ามไฟล์ที่มี mapping อยู่แล้ว** (`if document_id in mapping: skip`) — ถ้าต้องการ
บังคับให้อัปโหลดไฟล์ที่แก้ไขใหม่ทับของเดิม ต้องลบ entry ของ `document_id` นั้นออกจาก
`data/nhrc_pdf_drive_map.json` ก่อน (หรือลบไฟล์เก่าใน Drive เอง) แล้วค่อยรันสคริปต์ซ้ำ

## 5. ตัวแปรแวดล้อมที่เกี่ยวข้อง (`web/.env.local`)

ดูรายละเอียดเต็มใน `web/.env.example` สรุปเฉพาะที่เกี่ยวกับ pipeline นี้:

| ตัวแปร | จำเป็นสำหรับ |
|---|---|
| `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL` | AI สรุปคำตอบใน Ask NHRC และ "กฎหมาย/ตราสารที่เกี่ยวข้อง" ในหน้ากรณี (ไม่ตั้งไว้ = ระบบยังใช้ได้แต่ไม่มี AI สรุป) |
| `GEMINI_API_KEY` | สร้าง embeddings สำหรับ semantic search (ข้อ 4) |
| `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SECRET_KEY` | เก็บ embeddings |
| `IAPP_API_KEY` | ยืนยันมาตรากฎหมายไทยจริงจากฐานข้อมูล OpenThai 2.0 Legal (ไม่ตั้งไว้ = ใช้ความจำ AI ล้วน ต้องระวังความแม่นยำมากกว่า) |
| `GOOGLE_DRIVE_CLIENT_ID/SECRET/REFRESH_TOKEN` | เสิร์ฟไฟล์ PDF ต้นฉบับจาก Google Drive ในโปรดักชัน (`data/nhrc_documents/` ไม่ได้ขึ้นไปกับ deploy เพราะไฟล์ใหญ่/gitignored) |

## 6. การ deploy ขึ้นโปรดักชัน (Vercel)

```bash
npx vercel --prod --yes --scope bandits-projects-111dbe2a
```

**รันจาก root ของ repo (`D:\human-rights-rag`) ไม่ใช่จากใน `web/`** - การตั้งค่า Root Directory
ของโปรเจกต์นี้บน Vercel เองระบุไว้เป็น `web` อยู่แล้ว (มันจะ cd เข้า `web/` เองตอน build) ถ้า `cd web`
ก่อนรันจะได้ error `"The specified Root Directory \"web\" does not exist"` เพราะเท่ากับให้ Vercel
หา `web/web` ที่ไม่มีจริง (เคยเขียนคู่มือผิดไว้ว่าให้ `cd web` ก่อน - แก้แล้ว)

**ต้องระบุ `--scope`** แม้ `.vercel/project.json` จะผูก project ไว้แล้วก็ตาม — เคยเจอปัญหา
`{"status":"error","reason":"deploy_failed","message":"Not authorized"}` เพราะ token
ที่ login อยู่คนละ team scope กับที่ project ผูกไว้ ถ้าเจอปัญหานี้อีก รัน
`npx vercel teams ls` เพื่อดู scope slug ที่ถูกต้อง

## 7. ปัญหาที่พบบ่อยระหว่างพัฒนา/ทดสอบ

- **Dev server ชน port กับโปรเจกต์อื่นบนเครื่องเดียวกัน** — ถ้าเปิด `npm run dev` แล้ว
  เจอพฤติกรรมแปลก ๆ (API คืนหน้าเว็บผิด/ข้อมูลหน้าอื่น) ให้ตรวจว่ามี process อื่นถือ
  port 3000 ค้างอยู่หรือไม่ (`Get-NetTCPConnection -LocalPort 3000` ใน PowerShell)
  ก่อนไล่หาบั๊กในโค้ด — เคยเสียเวลาไปมากกับกรณีนี้เพราะมี dev server ของอีกโปรเจกต์
  (`thailand-human-rights-monitor`) ค้างอยู่บน port เดียวกัน
- **หน้าเว็บ error `LegalRefsBox is defined multiple times`** หรือ error คล้ายกันตอนแก้
  ไฟล์ — เป็น Turbopack fast-refresh ชั่วคราวระหว่างบันทึกไฟล์ กด reload อีกครั้งหลัง
  บันทึกเสร็จมักหายเอง ถ้าไม่หายให้ตรวจว่ามีการประกาศฟังก์ชัน/คอมโพเนนต์ชื่อซ้ำจริงในไฟล์
- **กราฟ (`/knowledge/graph`) ไม่มีข้อมูล** — ต้องรัน `python setup_obsidian_index.py`
  อย่างน้อยหนึ่งครั้งก่อน (สร้าง `data/nhrc_graph.json`)

## 8. เพิ่มหัวข้อใหม่ (เช่น "## เนื้อหาเต็ม") แล้ววางเนื้อหาเต็มของเอกสาร มีผลแค่ไหน

**อัปเดต (2026-08):** เดิมหัวข้อนี้เคยเตือนเรื่องขีดจำกัดความยาว 3,000/1,800 ตัวอักษร
นับจากต้นไฟล์ - ข้อจำกัดนั้น**ถูกแก้แล้ว** ด้วยระบบแบ่งเนื้อหาเป็นส่วน ๆ (chunking) ด้านล่าง
ตอนนี้เอกสารยาวแค่ไหนก็ใช้งานได้เต็มความยาว ไม่มีลิมิตตายตัวอีกต่อไป

**วิธีทำงานของ chunking:** `embed-nhrc-documents.mjs` แบ่งเนื้อหาไฟล์ยาว ๆ เป็นชิ้นละ
~3,000 ตัวอักษร (ตัดตามย่อหน้า ไม่ตัดกลางประโยค) แล้วฝัง (embed) แยกทีละชิ้นลง Supabase
(`nhrc_embeddings` - 1 แถวต่อ 1 ชิ้น ไม่ใช่ 1 แถวต่อ 1 เอกสารเหมือนเดิม) ตอนค้นหา ระบบจะหา
**ชิ้นที่ตรงที่สุด** ของแต่ละเอกสาร (ฟังก์ชัน `match_nhrc_documents` ใน
`supabase/nhrc_embeddings_schema.sql`) แล้วเอาชิ้นนั้น (ไม่ใช่ตัวต้นไฟล์) ไปเป็นเนื้อหาที่ AI
อ่านตอบคำถามโดยตรง (`route.ts`) - แปลว่าถ้าคำถามตรงกับเนื้อหาที่อยู่หน้า 150 ของรายงานยาว
2 ล้านตัวอักษร ระบบจะดึงหน้า 150 มาตอบ ไม่ใช่ดึงมาแค่หน้าแรกเหมือนแต่ก่อน (ทดสอบยืนยันแล้วจริง
กับ `situation_report_2566/2567.txt`)

เอกสารสั้น (ส่วนใหญ่ของคลังตอนนี้) ยังคงเป็น 1 ชิ้นเหมือนเดิมทุกประการ ไม่มีอะไรเปลี่ยน

**สรุปเชิงปฏิบัติ:** แปะเนื้อหาเต็มของเอกสารได้เลยไม่ว่าจะยาวแค่ไหน ระบบจะแบ่งชิ้นให้เองตอนรัน
`sync-content.bat` / `embed-nhrc-documents.mjs` - ไม่ต้องกังวลเรื่องลิมิตความยาวอีกแล้ว
`## สาระสำคัญ` ต้นไฟล์ยังคงมีประโยชน์อยู่ (คนอ่านหน้าเว็บเห็นก่อน และช่วยให้ทุกชิ้นของเอกสาร
เดียวกันมีบริบทหัวข้อ/คำสำคัญกำกับ) แต่ไม่ใช่เงื่อนไขบังคับสำหรับให้ AI ค้นเจอเนื้อหาส่วนอื่นอีกต่อไป

**ข้อควรรู้ - โควตา Gemini embedding:** การ (re-)embed เอกสารจำนวนมากหรือยาวมาก ๆ ในครั้งเดียว
(เช่น ใส่เนื้อหาเต็มของเอกสารหลายฉบับพร้อมกัน) อาจชนโควตารายวันของ Gemini API ถ้ายังใช้ free tier
(1,000 embedding requests/วัน) - ต้องเปิด billing (pay-as-you-go) บน API key ที่
[Google AI Studio](https://aistudio.google.com/app/apikey) ค่าใช้จ่ายต่ำมากเทียบกับปริมาณเนื้อหา
ถ้าชนโควตากลางทาง **ไม่มีอะไรเสียหาย** - สคริปต์บันทึกผลที่ทำเสร็จแล้วลง Supabase ทันทีทีละเอกสาร
(ไม่รอจนจบทั้งหมด) แค่รัน `sync-content.bat` ซ้ำอีกครั้งพรุ่งนี้ (หรือหลังเปิด billing) มันจะทำต่อ
เฉพาะเอกสารที่ยังไม่เสร็จเท่านั้น

## 9. ไฟล์ที่ไม่ใช่เนื้อหาเอกสาร (checklist/manifest) ถูกนำไปค้นหา/อ้างอิงด้วย

**สาเหตุ:** `_parse_generic` ใน `src/obsidian_parser.py` เดิมรับทุกไฟล์ `.md` ในโฟลเดอร์หมวดหมู่
(06-10) เป็น "เอกสาร" หมด ยกเว้นชื่อที่ตรงกับ `EXCLUDED_TITLES` แบบเป๊ะ ๆ เท่านั้น - ไฟล์ช่วยงานของ
ผู้ดูแลเอง เช่น ตารางเช็คสถานะการแปล (`00_บัญชีรายการและสถานะ.md`) จึงหลุดเข้าไปเป็น "เอกสารอ้างอิง"
ในผลค้นหา/คำตอบ AI ได้ทั้งที่ไม่มีเนื้อหาจริงอยู่เลย (**แก้ไขแล้ว** - ดูด้านล่าง)

**วิธีแก้ (แก้แล้วในโค้ด):** ไฟล์ที่ชื่อขึ้นต้นด้วย `00` (เช่น `00_...` หรือ `00 ...`) จะถูกตัดออกจาก
ดัชนีค้นหาโดยอัตโนมัติเสมอ ไม่ว่าจะอยู่โฟลเดอร์ไหน (ตามธรรมเนียมเดิมของไฟล์ `00 หน้าแรก.md` ที่มีอยู่
ก่อนแล้ว) **ถ้าจะเพิ่มไฟล์ checklist/manifest/บันทึกช่วยจำสำหรับตัวเองในอนาคต ให้ตั้งชื่อขึ้นต้นด้วย
`00` ตามธรรมเนียมนี้เสมอ** จะได้ไม่ต้องแก้โค้ดเพิ่มทุกครั้ง

รันแล้วเห็นผลจริง: `python setup_obsidian_index.py` (ตัดออกจากดัชนี + ลบไฟล์ `data/nhrc_content/*.txt`
ที่ไม่มีเจ้าของแล้วให้เองอัตโนมัติ) ตามด้วย `node scripts/embed-nhrc-documents.mjs` (ลบแถวใน Supabase
ของเอกสารที่หลุดออกจากดัชนีให้เองอัตโนมัติเช่นกัน - ไม่งั้นจะยังค้นเจอ/ถูกอ้างอิงต่อไปทั้งที่ไม่มีใน
ดัชนีแล้ว) ทั้งสองอย่างนี้ `sync-content.bat` รันให้ครบอยู่แล้วในคำสั่งเดียว

**ข้อสังเกตแยกต่างหาก - ชื่อไฟล์ซ้ำกันข้ามโฟลเดอร์ (แก้แล้ว):** ตรวจพบว่าโฟลเดอร์
`07 .../คำแปลภาษาไทย_ฉบับร่าง/` มีไฟล์ 6 ฉบับชื่อ**เดียวกันเป๊ะ**กับไฟล์ต้นฉบับที่มีอยู่แล้วในโฟลเดอร์
`07` ระดับบน (CAT, CEDAW, CRPD, CRC, ICCPR, ICESCR) เนื่องจาก document_id คำนวณจาก**ชื่อไฟล์เท่านั้น**
(ไม่รวม path โฟลเดอร์) ไฟล์ทั้งสองฉบับต่อคู่จึงชนกัน - เช็คแล้วมีแค่ฉบับแปลเต็มรอดเข้าดัชนีจริงทั้ง 6 คู่
(โน้ตสรุปเดิมหายไปเงียบ ๆ ไม่มี error เตือน)

ผู้ดูแลยืนยันแล้วว่าต้องการให้ฉบับแปลเต็มเป็นเนื้อหาหลักถาวร (แม่นยำ/ครบถ้วนกว่าโน้ตสรุป) จึง**เปลี่ยน
นามสกุลไฟล์ต้นฉบับเดิมทั้ง 6 ฉบับจาก `.md` เป็น `.md.bak`** (เติมคำว่า "แทนที่แล้ว"/"แทนที่ด้วยฉบับ
แปลเต็มแล้ว" ในชื่อไฟล์ด้วย) - **ไม่ได้ลบไฟล์ทิ้ง** เนื้อหาเดิมยังอยู่ครบ แค่เปลี่ยนนามสกุลให้พ้นจาก
`vault_path.glob("**/*.md")` ของ parser เท่านั้น ทำให้เลิกชนกันแบบถาวร ยังหาไฟล์เดิมเจอได้ในตำแหน่ง
เดียวกันถ้าต้องการเทียบเนื้อหา

**ข้อควรระวังสำหรับอนาคต:** เอกสารในโฟลเดอร์ `คำแปลภาษาไทย_ฉบับร่าง/` ตาม `00_บัญชีรายการและสถานะ.md`
ยังมีสถานะ "รอแปลและตรวจเทียบ" (ยังไม่ตรวจสอบ) - เนื้อหาที่เป็นเนื้อหาหลักตอนนี้จึงอาจมีจุดที่ OCR
ผิดพลาด (เช่น สระ/วรรณยุกต์หาย) ควรตรวจทานทีละฉบับเมื่อมีเวลา ถ้าเจอไฟล์ชื่อซ้ำแบบนี้อีกในอนาคต (เพิ่ม
เอกสารใหม่ในโฟลเดอร์ย่อยที่ชื่อไฟล์ตรงกับของเดิม) จะเกิดปัญหาเดียวกันซ้ำอีก - วิธีป้องกันไว้ก่อนคือตั้ง
ชื่อไฟล์ให้ไม่ซ้ำกันตั้งแต่แรกข้ามทั้งวอลต์ ไม่ใช่แค่ในโฟลเดอร์เดียวกัน

## 11. บั๊กที่พบระหว่างแก้ข้อ 10: การลบ orphan ใน Supabase ไม่ครบ (แก้แล้ว)

**อาการ:** หลังรันแก้ข้อ 10 แล้ว (log บอก "Removed 22 orphaned document(s)") ยังพบ `topic_C_สิทธิเด็ก`
โผล่มาในคำตอบ Ask NHRC อยู่ดี ตรวจสอบตรงกับ Supabase พบว่ายังมีแถว embedding ของโน้ต topic เหลืออยู่
3 รายการ (6 chunk rows) ที่ไม่ถูกลบ

**สาเหตุ (สำคัญ ควรรู้ไว้):** `web/scripts/embed-nhrc-documents.mjs` ใช้ `.select("document_id,
content_hash")` แบบไม่ใส่ `.range()`/pagination - **Supabase/PostgREST จะตัดผลลัพธ์ที่ 1,000 แถว
โดยอัตโนมัติแบบไม่มี error หรือคำเตือนใด ๆ ทั้งสิ้น** ตาราง `nhrc_embeddings` ตอนนี้มีมากกว่า 3,000
แถว (เพราะระบบ chunking) การ query แบบไม่แบ่งหน้าจึงเห็นแค่ 1,000 แถวแรก ทำให้ตรรกะลบ orphan
(เทียบ id ที่มีอยู่ใน Supabase กับ id ที่ควรมีจริงในดัชนี) มองไม่เห็นเอกสารที่อยู่นอกช่วง 1,000 แถวแรก
เลย - ไม่ใช่แค่เรื่อง orphan เท่านั้น ยังกระทบตรรกะ "ข้ามเอกสารที่ไม่เปลี่ยน" (content_hash) ด้วย
(เอกสารที่ตกหล่นจากการนับจะถูกฝัง embedding ซ้ำทุกครั้งที่รัน ทั้งที่เนื้อหาไม่ได้เปลี่ยนเลย)

**แก้ไขแล้ว:** เปลี่ยนเป็น query แบบวนอ่านทีละหน้า (`.range(from, from+999)` วนจนกว่าจะได้แถวน้อยกว่า
1,000 แถวในหน้านั้น) - ครอบคลุมทุกแถวจริงไม่ว่าตารางจะโตแค่ไหน ทดสอบแล้ว: รันซ้ำหลังแก้ไข ลบ orphan
ที่เหลือ 3 รายการออกจนหมด ยืนยันด้วย query ตรงจาก Supabase ว่าไม่มีแถว `topic_%` เหลือเลย

**ข้อควรระวังสำหรับสคริปต์ admin ในอนาคต:** ถ้าจะเขียนสคริปต์ที่ query ตาราง `nhrc_embeddings` (หรือ
ตารางอื่นที่มีแนวโน้มโตเกิน 1,000 แถว) ต้องใส่ pagination ทุกครั้ง ไม่งั้นจะเจอบั๊กแบบนี้ซ้ำแบบเงียบ ๆ
โดยไม่มีอะไรเตือนเลย (ฟังก์ชัน RPC อย่าง `match_nhrc_documents` ที่ค้นหาจริงตอนใช้งานเว็บไม่กระทบ
เพราะมี `limit` กำกับอยู่ในตัว SQL function เองอยู่แล้ว - กระทบเฉพาะสคริปต์ฝั่ง admin ที่ query ตรง
แบบนี้เท่านั้น)

## 12. Ask NHRC ตอบแบบ streaming + แสดงสถานะการค้นหาแบบ real-time

**ที่มา:** ผู้ใช้รายงานว่า "เว็บค้นหาช้า" และอยากให้มีตัวแสดงสถานะระหว่างรอ แบบเดียวกับ
fourcorners.law (ขึ้นข้อความบอกว่ากำลังทำอะไรอยู่ระหว่างรอคำตอบ แทนที่จะเงียบแล้วโผล่คำตอบทีเดียว)

**สิ่งที่ทำ:** `web/src/app/api/ask-nhrc/route.ts` เปลี่ยนจากตอบ JSON ก้อนเดียว (`NextResponse.json`)
เป็นตอบแบบ stream (newline-delimited JSON ทาง `ReadableStream`, ไม่ใช่ SSE เพราะเป็น POST ไม่ใช่
`EventSource`) โดยส่ง event ทีละบรรทัดตามลำดับที่เกิดขึ้นจริง:

1. `{"type":"status","message":"กำลังค้นหาเอกสาร..."}` - ก่อนเริ่มค้น semantic search
2. `{"type":"status","message":"พบเอกสาร N รายการ กำลังวิเคราะห์..."}` - หลังค้นเจอ ก่อนสร้าง excerpt
3. `{"type":"citations","citations":[...]}` - ส่งรายการอ้างอิงทันทีที่พร้อม (ไม่ต้องรอ AI เขียนคำตอบเสร็จ)
4. `{"type":"status","message":"กำลังเรียบเรียงคำตอบด้วย AI..."}` - ก่อนเรียก Claude
5. `{"type":"delta","text":"..."}` - ทีละท่อนข้อความจาก Claude (`client.messages.stream()` แทน
   `.create()`) ยิงมาเรื่อย ๆ ระหว่างที่ AI กำลังเขียนคำตอบ
6. `{"type":"done","mode":"llm-rag"}` - จบสตรีม

ฝั่งหน้าเว็บ (`nhrc-workspace.tsx`'s `runAsk`) อ่าน stream ด้วย `res.body.getReader()` เอง (ไม่ใช้
`res.json()`) ต่อ event ทีละบรรทัด แล้วอัปเดต UI ตามชนิด event: `status` → ข้อความสถานะ +
จุดกระพริบ 3 จุด (`.cw-status-bubble`/`.cw-status-dots`, `chat-workspace.css`), `delta` → เติมข้อความ
คำตอบสะสมทีละท่อนพร้อม caret กระพริบท้ายบรรทัด (`.cw-typing-caret`) ให้ดูเหมือนกำลังพิมพ์อยู่จริง

**ผลที่ได้ 2 อย่าง จากการเปลี่ยนจุดเดียว:**
- **เห็นสถานะจริง ไม่ใช่ animation หลอก** - ข้อความสถานะแต่ละอันส่งเมื่อ stage นั้นเริ่มทำงานจริง
  ไม่ใช่ตั้ง timer ฝั่ง client แล้วเดาว่าน่าจะถึงไหนแล้ว
- **เร็วขึ้นในทางที่ผู้ใช้รู้สึกได้จริง (perceived latency)** - เดิม `.create()` ต้องรอ Claude เขียน
  คำตอบครบ (สูงสุด 6144 token) แล้วส่งกลับทีเดียว ทำให้ user เห็นจอเงียบ 10-20+ วินาที ทั้งที่ token
  แรกของคำตอบมาจริง ๆ ภายใน 2-3 วินาทีหลังเรียก Claude - เปลี่ยนเป็น streaming ทำให้ผู้ใช้เห็นคำตอบ
  เริ่มไหลออกมาเร็วกว่าเดิมมาก แม้เวลารวมจนคำตอบจบจะพอ ๆ เดิมก็ตาม (นี่คือส่วนที่แก้ได้จริงโดยไม่ต้อง
  แตะ semantic search/Supabase - ถ้ายัง "รู้สึกช้า" อยู่ ให้เช็คเวลาแต่ละ stage จาก log ฝั่ง server
  ก่อนว่าจุดไหนช้าเป็นพิเศษ เช่น semantic search เอง, หรือ cold start ของ serverless function)

**ถ้าจะแก้/เพิ่ม stage ในอนาคต:** เพิ่ม `send({ type: "status", message: "..." })` ตรงจุดที่ต้องการใน
`route.ts` ได้เลย ฝั่ง client จะรับและแสดงอัตโนมัติโดยไม่ต้องแก้โค้ด UI เพิ่ม (เว้นแต่จะเพิ่ม `type`
ใหม่ที่ไม่ใช่ `status`/`citations`/`delta`/`done`/`error`)

## 13. ตัวกรองย่อยในแต่ละหมวดเอกสาร (sub_type/result) - เพิ่มประเภทเอกสารใหม่แล้วไม่ต้องแก้โค้ดเว็บ

**ที่มา:** ผู้ใช้อยากให้หน้า browse ของแต่ละหมวดเอกสารมีตัวกรองย่อยแบบเว็บ fourcorners.law
เช่น หมวด "กฎหมายไทย" กรองด้วย "ประเภทกฎหมาย" (รัฐธรรมนูญ/พ.ร.บ./พ.ร.ก./...), หมวด "กฎหมาย
สิทธิมนุษยชนระหว่างประเทศฯ" กรองด้วย "ประเภทตราสาร" (ปฏิญญา/สนธิสัญญา/พิธีสาร/ความเห็นทั่วไป),
หมวด "รายงานตรวจสอบ/ข้อเสนอแนะ กสม." กรองด้วยทั้ง "ประเภทเอกสาร" และ "ผลการตรวจสอบ" - และเมื่อ
เพิ่มเอกสารประเภทใหม่ในอนาคต (เช่น พ.ร.ก., กฎกระทรวง) ให้ตัวกรองโผล่มาเองโดยไม่ต้องแก้โค้ดเว็บเลย

**สถาปัตยกรรม (data-driven ทั้งสาย ไม่มี list ตายตัวในโค้ดเว็บ):**

1. **`src/obsidian_parser.py`** เติม 2 ฟิลด์ใหม่ในทุก document dict:
   - **`sub_type`** - มาจาก frontmatter `law_type` (หมวด 06)/`instrument_type` (หมวด 07)/
     `sub_type` ตรง ๆ (หมวดอื่นในอนาคต) ผ่าน `_normalize_law_type`/`_normalize_instrument_type`
     ซึ่งลดรูปข้อความยาว ๆ ให้เหลือ bucket สั้น ๆ (ดู comment เหนือ `INSTRUMENT_TYPE_PREFIX_BUCKETS`/
     `INSTRUMENT_TYPE_KEYWORD_BUCKETS` ในไฟล์ - ค่าจริงใน `instrument_type` ของไฟล์ความเห็นทั่วไป
     เป็นประโยคยาวเฉพาะคณะกรรมการ ถ้าใช้ตรง ๆ จะได้ตัวกรอง ~15 อันซ้ำซ้อนแทนที่จะเป็น 4 อันตามที่ต้องการ)
     ถ้าไฟล์ไม่มี frontmatter พวกนี้เลย (เช่นไฟล์แปลเต็มใน "07 .../คำแปลภาษาไทย_ฉบับร่าง/" ที่มีแค่
     `title:`/`source_file:`) จะเดา sub_type จากชื่อเรื่องแทน (`_infer_sub_type_from_title` - จำกัด
     เฉพาะไฟล์ในโฟลเดอร์ "07" เท่านั้น ป้องกันคำอย่าง "อนุสัญญา"/"ปฏิญญา" ไปจับผิดกับงานวิจัยที่แค่
     พูดถึงตราสารนั้นในชื่อเรื่อง)
   - **`result`** (เฉพาะ case_note) - อ่านจากบรรทัด `**ผลการพิจารณา:** ...` ในเนื้อหาบันทึกกรณี
     (ข้อความอิสระ ไม่มี controlled vocabulary) แล้วลดรูปด้วย `_extract_case_result`/
     `CASE_RESULT_PREFIX_BUCKETS` เป็น bucket กว้าง ๆ (ละเมิดสิทธิมนุษยชน/ไม่ละเมิด/ยุติเรื่อง/
     ไม่อาจรับฟังได้ว่าละเมิด/อื่นๆ) โดยดูจาก "คำแรก" ที่เขียนไว้จริง - **นี่คือการจัดกลุ่มคร่าว ๆ
     สำหรับกรองเท่านั้น ไม่ใช่การตัดสินคดีใหม่** ผลจริงแบบละเอียด (มีหลายประเด็นย่อยผลต่างกันในคดี
     เดียวก็มี) ยังอยู่ในเนื้อหาเต็ม/excerpt ที่แสดงในการ์ดเสมอ
2. **`web/src/lib/nhrc/repository.ts`**'s `search()` กรองด้วย `query.subType`/`query.result` และคำนวณ
   `facets: { subType: Facet[], result: Facet[] }` (นับจำนวนเอกสารต่อค่าที่พบจริงในผลลัพธ์ปัจจุบัน -
   ไม่มี list ตายตัว) ส่งกลับมาพร้อม `data`/`pagination` ทาง `/api/search/hybrid`
3. **`nhrc-workspace.tsx`** เก็บ facets ที่ได้จาก API ไว้ใน state แล้ว render เป็นกลุ่มปุ่มกรอง
   (`.cw-facet-panel`) **เฉพาะเมื่อ facets นั้นไม่ว่าง** - หมวดที่ไม่มี sub_type/result เลย (เช่น
   งานวิจัย) จะไม่มีตัวกรองใด ๆ ขึ้นมาโดยอัตโนมัติ ป้ายชื่อกลุ่มตัวกรอง sub_type ("ประเภทกฎหมาย"/
   "ประเภทตราสาร"/"ประเภทเอกสาร") มาจาก `SUB_TYPE_FACET_LABELS` ในไฟล์นี้ - แค่ความสวยงาม ถ้าเพิ่ม
   หมวดใหม่ที่ไม่ได้อยู่ใน map นี้ จะขึ้นป้ายกลาง ๆ ว่า "ประเภทย่อย" แทน ยังใช้งานได้ปกติ

**เพิ่มเอกสารประเภทใหม่ในอนาคต (เช่น "กฎกระทรวง") แล้วอยากให้มีตัวกรองอัตโนมัติ - ทำแค่นี้:**
ใส่ `law_type: "กฎกระทรวง"` ใน frontmatter ของไฟล์ตามเทมเพลต แล้วรัน `sync-content.bat`/
`setup_obsidian_index.py` ตามปกติ - ตัวกรอง "กฎกระทรวง" จะโผล่ในกลุ่ม "ประเภทกฎหมาย" เองพร้อมจำนวน
เอกสาร ไม่ต้องแก้โค้ดเว็บแม้แต่บรรทัดเดียว (เว้นแต่ค่าที่ใส่ไม่ตรงกับ bucket ที่รู้จัก - กรณีนั้นจะ
ตกไปที่ "อื่นๆ" แทน ยังใช้กรองได้ปกติ เพียงแต่ป้ายไม่เจาะจง)

**ข้อควรระวังการทดสอบ dev server หลังแก้ API route:** เจอเคสที่ restart dev server ด้วย
`preview_stop`/`preview_start` ติดกันเร็ว ๆ แล้ว `.next/` cache ค้าง ทำให้ทุก route ใต้ `/api/*` ตอบ
404 หมด (ทั้งที่ route เดิมทำงานถูกต้องก่อน restart) - ไม่ใช่บั๊กจากโค้ด แก้ด้วยการลบ `web/.next/`
ทิ้งแล้ว start ใหม่ครั้งเดียว
